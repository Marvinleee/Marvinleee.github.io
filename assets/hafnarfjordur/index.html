一个关于开放地理数据「看起来很精确，其实大量推算」的现场演示

先看数字

屏幕上共 — 栋建筑。其中高度来自 OpenStreetMap 的 height 标签的： — 栋。

也就是说，你看到的几乎整个城市天际线—— — 栋楼的高度——都是推算出来的。

高度是怎么来的

开放数据里一栋楼的高度有三个来源，可靠性依次递减：

  • 实测（height）：有人真的量过或查过图纸。本区 0 栋。
  • 楼层数推算（building:levels）：知道有几层，按每层约 3.2 米折算。本区 — 栋。
  • 类型与面积估算：既无高度也无层数，只能按建筑用途和占地大小猜。本区 — 栋。

最后一档的规则示例：车库 3 米；独栋住宅按占地分档 6–9 米；公寓楼按占地开方推层数（约 2–6 层）再乘 3.2 米；教堂 16 米、厂房 9 米。

为什么这里几乎没有数据

众包地理数据的完整度与「当地有多少人愿意录入」强相关。首尔市中心约 10% 的建筑带高度标签； 而这座三万多人的冰岛港口城市，几乎无人标注高度——全城 2891 栋里只有 1 栋。

把配色切到「数据来源」，整片城区会变成灰蓝色：那就是被推算的部分。

但「低平」本身是真实的

值得注意的是，本区已知层数的建筑集中在 1–2 层（71 栋）与 4 层（25 栋）， footprint 中位数仅 142 m²。这是一座真实的低层小城， 所以把大量建筑估成 6–7 米，误差远小于在摩天楼城市里做同样的估算。 平坦的天际线不是数据缺陷造成的假象，它就是这座城市的样子。

另外两处诚实声明

  • 高度被夸张了：默认 4×。因为 6 米的房子放在 1.5 公里的场景里几乎是平的。滑块可以调回 1× 看真实比例。
  • 轮廓是简化过的：只保留 footprint 外轮廓，屋顶结构、女儿墙、附属物一概没有。

数据链路

Overpass API 取 OSM building 要素 → 坐标相对原点量化为分米整数 → 高度分档赋值并标记来源 → 打包后 gzip 约 — → 浏览器端还原轮廓、挤出体块、合并为单个几何体渲染。
